# A7 — flooding: what a forged frame costs a receiver, and what stops it

*Registered 2026-10-20 before any timing of the paths below. Plan: `docs/AUTHBC Revision
Plan.md`, A7. Outcome appended below a line at the end.*

## What is built

`src/authbc/placement/admission.py` (tests `tests/unit/placement/test_admission.py`): a layer
in front of the timed receiver, applying in order an optional 8 B group HMAC envelope (zero
change to the frame format: the tag wraps it), cheap checks (length, CBOR shape, known sender,
sequence window), a per-sender token bucket, then `LeanReceiver`. The plan's worst-case attack
frame — well formed, naming a real sender, a newer sequence number, a wrong signature — is held
by a test to pass every cheap check and cost a verification.

## What is run — on pi-B (open item H4); a quiet-host run is reported separately as the host's

The plan's design: the existing receiver fed through a local UDP socket, radio out of the loop;
honest load 124 senders × 12.5 frames/s; attack 0–3 000 frames/s; mitigations: none, cheap
checks, per-sender cap, group HMAC, and Ed25519 batch verification (64 per batch; the Python
library has no batch verification, so this row uses the C timing of `hw/ed25519_batch`, which
measured 0.46 of the per-signature cost on pi-B). Metrics: per-frame cost of each path, the
receiver's core share, honest V against attack rate, the attack rate at which honest V falls
below 0.95. Harness: `analysis/flood_cost.py` (written before the run, committed with its
outcome; the paths it times are the ones the unit tests define).

## Computed before this registration

The 8 B tag lengthens the design's frame from 173 to 181 B: the no-fit closed form's capacity
falls from 126.7 to 122.8 nodes (−3.1 %), Eq. (6)'s from 125.0 to 121.8 (−2.6 %).

## Predictions — the plan's, verbatim

> - With no mitigation, about 700 fake frames/s saturate one core of the Python receiver
>   (1.43 ms per frame).
> - With the group HMAC, an outsider needs more than 100 000 frames/s to saturate a core, which
>   the channel cannot carry. Outsider flooding is effectively removed.
> - An insider holding a valid swarm key remains a threat; the per-sender cap limits that damage
>   to the sender being impersonated.
> - The HMAC's 2 bytes per record reduce Nmax by about 2% (by equation 6).

## Mine `[agent]`

* **A7-1.** A forged frame costs within 10 % of an honest one (it is decoded, rebuilt and
  verified alike; it is refused only at the signature): ≈ 1.4 ms on pi-B, so one core saturates
  at ≈ 700 forged frames/s, as the plan says.
* **A7-2.** The HMAC check costs under 20 µs per frame in Python on pi-B (one HMAC-SHA256 over
  ~180 B plus the call): an outsider needs > 50 000 frames/s per core — more than the channel
  carries (a 181 B frame takes ≈ 0.35 ms on air: < 3 000 frames/s). Held: "effectively removed".
* **A7-3.** The tag costs 3 % of capacity by the no-fit closed form (computed above), not 2 %:
  the plan's figure is Eq. (6) with a 2 B-per-record rounding.
* **A7-4.** Cheap checks alone stop nothing of the worst-case frame (by construction it passes
  them); they stop replays and garbage at a parse's cost (≈ 0.1 ms in Python).
