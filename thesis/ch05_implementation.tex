\chapter{Implementation}\label{ch:implementation}

The system is a Python library of nearly eight thousand lines, the scripts that run it, two
simulation scenarios and a hardware harness. This chapter describes what was built and the
rules it was built to; \Cref{app:repro} says how to run it.

\section{Design rule: one home per fact}

The implementation follows one architectural rule that is worth stating because it is what makes
the reproducibility claims of \Cref{ch:reproducibility} possible. \textbf{Every quantity has
exactly one definition, and everything else refers to it.} There is one function that produces the
canonical bytes a signature covers; one airtime implementation shared by the channel model, the
energy model and the simulation comparison; one place where experiment parameters live.

Where that rule was broken, defects followed. A signature-size constant duplicated between two
modules produced a stale result that survived a re-freeze. An airtime approximation that existed in
two forms produced a $12\%$ discrepancy on acknowledgement frames. And the largest instance was
not a duplicated constant but a \emph{missing object}: for three months the design the results
headlined existed only as a sum of sizes measured in three modules, with no frame, no sender and
no receiver behind it --- so the byte model, the verifiability model and the exclusion test each
evaluated a slightly different thing and none could be checked against the others
(\Cref{ch:reproducibility}).

\begin{description}
\item[\texttt{encodings/}] The $e$ axis: JSON, canonical CBOR (RFC 8949, Section~4.2), MessagePack, and
delta-CBOR with keyframes every $K = 16$. Delta encoders are \emph{stateful}; a fresh instance per
record emits all keyframes and silently inflates sizes --- a trap that cost real time.

\item[\texttt{crypto/}] The $\sigma$ axis: Ed25519 and ECDSA-P256 (both $64$\,B), BLS12-381
($96$\,B). Known-answer tests from RFC 8032, NIST CAVP and the IETF BLS draft are vendored and must
pass before any timing work.

\item[\texttt{ledger/}] The data structure being authenticated: the canonical record, the hash
chain, persistence, and verification with replay and equivocation detection.

\item[\texttt{placement/}] The placement axis. \texttt{wire.py} is the first frame format and the
one place that decides \emph{what bytes a signature covers} --- the audit boundary; it is frozen.
\texttt{framer.py} holds its header constant and the batch bounds. \texttt{wire\_v2.py} is the
lean format of \Cref{sec:formats}: integer keys, one chain link per frame, a variable-length
record stream, and the same signed bytes as the first format. \texttt{session\_v2.py} is the
protocol around it --- a sender that emits one self-contained frame per reference interval, and a
receiver that decodes, verifies, stores and reports what it did with each frame (accepted,
desynchronised, malformed, unknown sender, bad signature, replay, equivocation, tampered).

\item[\texttt{models/}] The analytical layer: the DCF fixed point with exact OFDM-symbol airtime,
the published broadcast model, the energy and freshness models, the Pareto search, the scheme
crossover, and the low-rate PHY with every constant transcribed from primary specifications.
\texttt{frame.py} holds the \emph{one} definition of a frame from which the byte, verifiability
and exclusion results are all computed, and whose arithmetic is held equal to emitted frames by
test. \texttt{phy.py} makes the OFDM timing a parameter.

\item[\texttt{sim/}] Two simulators written for this work, neither of which shares code with
ns-3. A slot-exact backoff simulator of the saturated channel, written \emph{before} the
published broadcast model was located and retained as a cross-check that shares none of that
model's assumptions (\Cref{ch:validation}). And an event simulator of the access rule for a
lightly loaded channel --- arrivals, carrier sense, backoff counters and nothing else --- which
is the model of \Cref{sec:why}.

\item[\texttt{channel/}] Airtime of a frame from its length, and the loss processes of the
verifiability experiments: independent, bursty, and growing with frame length.

\item[\texttt{bench/}] The experiments. Each reads a configuration file, runs the library and
writes one result file with a header that records the environment and a hash of the
configuration. The telemetry generator of \Cref{sec:telemetry} and the timing rules of
\Cref{sec:rules} live here.
\end{description}

\section{Wire format}

\[
\text{Frame} := \{v, t, \texttt{src}, \texttt{base\_seq}, n, \texttt{recs}[\,], \texttt{auth}\}
\]
in canonical CBOR, with the authentication block shaped by placement. The signature input is the
canonical bytes of the covered region, and test vectors are frozen. The lean format keeps that
signature input and changes only how the records travel; its field table is \Cref{tab:fields}.

Reading it against \Cref{tab:fields}: the map header, the five scalar fields and the two
three-byte prefixes of the record stream and the signature are the $23$\,B header; the link and
its prefix are $35$\,B; the signature is $64$\,B. The first record carries absolute values and
takes $25$\,B here --- five bytes each for latitude and longitude, which is where a keyframe's
size goes --- and the second carries nine differences in nine bytes. A third and a fourth record
would add nine bytes each, which is the whole of the design's saving: $23 + 35 + 64 = 122$\,B
of the frame are paid once however many records follow.

The values are variable-length integers, seven bits to a byte, signed ones folded so that small
magnitudes of either sign stay short. Nothing in the stream says where a record ends: a record
is nine integers, and the count $n$ says how many records there are.

\section{Sender and receiver}\label{sec:protocol}

The sender takes its own records in order, $b$ at a time, and emits one frame per batch. One
frame in every $r$ starts with a keyframe and decodes alone; with $r > 1$ the others start with
a delta against the last record of the frame before. The design uses $r = 1$.

The receiver does five things to a frame, in an order that matters. It reads the sender
identifier and decodes the record stream --- against the last record it \emph{accepted} from that
sender, if the frame is a dependent one. It rebuilds the canonical ledger records, taking the
first record's link from the frame and computing each later one as the hash of the record just
rebuilt. It verifies the signature over those records. It offers each record to the store, which
accepts only a sequence number newer than the last one stored for that sender. And only if every
record was stored does it advance the state against which a later dependent frame would be
decoded. A frame is signed as a unit, so it is accepted or refused as a unit.

{\small
\noindent\begin{tabularx}{\textwidth}{@{}l Y@{}}
\toprule
outcome & when \\
\midrule
accepted & decoded, verified, every record stored \\
desynchronised & well formed, but coded against a record this receiver does not hold \\
malformed & not a frame of this format \\
unknown sender & no public key held for the sender identifier \\
bad signature & the rebuilt records do not verify under the sender's key \\
replay & a sequence number not newer than the last one stored; nothing is stored \\
equivocation & a validly signed record for a sequence number already stored with different
content; both are kept, as evidence \\
tampered & verified, but its chain link contradicts a record the store holds \\
\bottomrule
\end{tabularx}
}

\vspace{0.5em}
\noindent Two properties follow from the order and are held by tests. Nothing unverified is
ever stored, because storing comes after verifying. And a replayed or forged frame cannot move
the decoding state, because that state advances only on acceptance; were it to advance on a
frame that merely decoded, replaying an old self-contained frame would rewind it and
desynchronise an honest sender's stream.

\section{Tests}\label{sec:tests}

The tests are in layers, and the layers catch different things.

\begin{description}
\item[Published vectors.] Each signature scheme must reproduce the test vectors of its
specification before it is timed or used; the frame formats have vectors of their own, frozen
when each format was fixed.
\item[Properties.] Round trips for every encoding over generated records; every single-bit
change to a frame must make verification fail, tried at every bit position of a design frame;
a frame that cannot be decoded must not be stored.
\item[The reproduction gate.] Every derived result file is recomputed from the committed raw
data and compared row by row (\Cref{sec:pipeline}).
\item[Text against data.] The numbers in the paper and in this thesis are macros written by a
script from the result files. What is typed --- a figure quoted from a frozen artifact, a
sentence that states a verdict --- is held to its artifact by a test, and a sentence the data no
longer support stops the build.
\item[The environment.] A test reads every import in the code and requires the package to be
declared, added after the gate passed on the author's machine and failed on a clean one.
\end{description}

\noindent What the layers do not catch is the subject of \Cref{ch:reproducibility}: a green
suite is a statement about the questions the tests ask.

\section{The two-layer data pipeline}\label{sec:pipeline}

The pipeline splits deliberately. \textbf{Measured} artifacts --- hardware timings, simulation
outputs --- are non-deterministic, so they are measured once under controlled conditions, committed
with environment and configuration-hash headers, and never silently re-rolled. \textbf{Derived}
artifacts are byte-stable functions of those, so an automated gate re-computes every one of them on
every run and fails if a single row differs.

This buys reproducibility at the price of \emph{silent staleness} risk: a frozen artifact can go
stale when an upstream decision changes and the artifact is not re-run. That is not hypothetical
--- it is exactly what produced the project's first recorded defect. The gate exists because the
risk is real.
