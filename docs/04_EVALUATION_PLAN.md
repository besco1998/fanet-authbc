## 1. Parameter measurement methodology (P1, repeated on RPi4 in P7)
- **Sizes s:** encode 10,000 synthetic telemetry records (realistic ranges: lat/lon
  1e-7 deg fixed-point, alt cm, vel cm/s, battery %, mode enum; generator seeded);
  report mean±CI and max per encoding; delta reported at K=16 with keyframe amortization.
  ⚠️ **The sampling WINDOW is part of the measurement (2026-08-28).** `seq` and `ts` grow with the
  record index, and canonical CBOR/JSON/MessagePack charge for the extra digits, so *s* depends on
  how long the generator runs: cbor 66.7 B at n=1000 and 68.9 B at n=10 000; json 191.4 → 193.5;
  msgpack 66.3 → 68.8. **Delta is flat** (45.04 → 45.01) because it encodes differences. E1 uses
  30 seeds × 1000 records — the **first ~50 s of each flight** — and that is what feeds the
  headline. ⚠️ Its bootstrap CI (cbor ±0.02 B) describes *seed* variation while this systematic
  term is ~2.7 B, **≈150× wider**; do not quote the CI as the uncertainty on *s*. The direction is
  conservative: a longer flight inflates the CBOR baseline and leaves delta alone, so the reported
  saving is the pessimistic end. This is why `p1_sizes.csv` (seed 1, n=10 000) and
  `e1_dominance.csv` (30×1000) differ by up to 3.7 B on the same named quantity — both are
  correct for their own protocol. Pinned by
  `tests/test_math_audit.py::TestRecordSizeDependsOnRunLength`.
- **Crypto times:** per scheme: keygen excluded from hot path; t_sg, t_vf on 200 B msgs;
  BLS t_ag(b), t_av(b) for b∈{2,4,8,16,32}; harness = doc 03 bench rules. Sanity anchors
  (x86 order-of-magnitude): Ed25519 sign ~15–60 µs, verify ~40–120 µs; ECDSA-P256 verify
  ~80–300 µs; BLS pairing verify ~1–3 ms. If measurements fall far outside, STOP and
  investigate the harness before recording.
- **Cross-platform anchor (REVISED at P7b, 2026-07-28).** The original "RPi4 is 5–15× slower
  than x86" is **withdrawn: it is arithmetically unreachable.** A wall-clock ratio is the product
  of the clock-frequency ratio and the per-cycle instruction efficiency, and the clock ratio alone
  (x86 4.7 GHz ÷ RPi4 1.8 GHz = **2.61×**) is a hard floor. Any primitive equally well optimised on
  both ISAs therefore *must* land near 2.61× and below the old band — measured: Ed25519 needs
  **1.05× the cycles** on ARM and lands at 2.73× wall. The anchor is restated **per-cycle**, which
  is platform- and clock-independent:
  **expect 1–4× the CYCLES on ARM** (portable, well-optimised code ≈1×; code exploiting
  ISA-specific assembly higher). Measured at P7b: Ed25519 1.05–1.16×, ECDSA-P256 1.60–1.98×,
  BLS 3.2×. Convert to a wall-clock expectation as `cycles_ratio × (f_x86 / f_ARM)`.
  Outside 1–4× cycles ⇒ STOP and investigate (governor, throttling, a different code path).
- **Airtime:** analytic (doc 02 §6) in the emulator; validated against NS-3 in E5.

## 3. NS-3 campaign (P6)
Scenario `authbc-sat.cc`: 802.11a ad-hoc, ConstantRateWifiManager OfdmRate6Mbps, RTS/CTS
off, N saturated senders in **both** modes (unicast with ACKs, broadcast without), frame
sizes taken from the real framer outputs, **10 s runs × 10 seeds** over N∈{5,10,20,35,50}.
Transport is **PacketSocket + PacketSink**, not FlowMonitor: we need MAC-level goodput with no
ARP/IP artifacts, and the accounting is provably exact (audit A12). Parse via the committed
`ns3/parse_ns3.py` / `ns3/run_matrix.py`; never hand-copy numbers.

Compare each mode ONLY to its matching analytic variant: unicast ↔ ACK-Bianchi, broadcast ↔
**Ma & Chen** (docs/02 §6a) — *not* the unicast model with the ACK removed, which fails by 16×.
Report the gap and its causes; correction factors documented, never silently applied. Measured
causes to date: **F8** sinks outliving sources (~4.8 %), **D9** airtime quantisation (0.41 %/12.1 %),
and the Consecutive Freeze Process (the 16×). Frame **capture is measured at 0 %** in this
scenario and is not a gap source. `make sim-ns3-matrix` / `make sim-ns3-dcf`; runtime ≪ 2 h.

## 4. RPi4 hardware campaign (P7, schedule-flexible)
4× RPi4 (Bookworm 64-bit, performance governor, headless). Steps: (i) rerun P1 micro
suite → hardware timing tables; (ii) energy: external USB meter (⚠️ D5: UM25C ≈ $30,
1 needed) — protocol: measure idle baseline 60 s, then each op in a 60 s tight loop,
energy/op = (P_loop − P_idle)·t_loop/n_ops, ≥5 repetitions; (iii) 2-node real-802.11
ad-hoc broadcast sanity run of the golden integration scenario (loss measured, not
injected) — qualitative validation only, small-N honesty stated. Feeds measured
(t_*, P_c, P_r) back into E4/E5 model re-runs → the hardware-grounded tables.

## 5. Reporting standards
Every figure: caption states config hash, seeds, CI type; every table: median (CI);
every claim in the paper maps to an experiment ID; negative/unexpected results are
reported (e.g., if BLS beats Ed25519 somewhere unpredicted, that is a finding, not a bug
to hide). A `results/PROVENANCE.md` maps every figure → config → commit.
